    Connections

    • Visitor's browser → GitHub Pages (HTTPS requests): The browser fetches pages, CSS and JavaScript from GitHub Pages.
    • GitHub Pages → Cheat sheet page (serves): /python-cheat-sheet/ is served as static HTML.
    • GitHub Pages → Playground page (serves): /python-playground/ and its scripts are served as static files.
    • Cheat sheet page ↔ Lesson cross-links (practice): Each section's Practice link goes to /python-playground/#lesson-id.
    • Lesson cross-links ↔ Playground page (#lesson): The playground opens the lesson named in the URL hash, and links back to the matching cheat sheet section.
    • Playground page → Code editor (CodeMirror 6) (create()): The page mounts the editor and reads code from it on Run and Check.
    • Lessons data (lessons.js) → Playground page (LESSONS): The page reads lesson text, starter code and checks from lessons.js.
    • Playground page ↔ Python worker (worker.js) (postMessage): The page sends {code, check}; the worker streams output back, then a done message with any error and the check result.
    • Python worker (worker.js) → Pyodide runtime (CDN) (loads): The worker loads pyodide.js from the CDN, then calls loadPyodide().
    • Python worker (worker.js) → Check logic (run_check()): When Check is pressed, the worker runs the lesson's check after the visitor's code.
    • Lessons data (lessons.js) → Check logic (assertions): Each lesson's check code (assert statements with hint messages) is what run_check executes.

    Visitor's browser Browser

    Where everything actually runs: the pages, the editor, and Python itself.

    What it does

    Downloads the static pages from GitHub Pages and runs all of the code locally, including Python, through Pyodide in a Web Worker. Lesson drafts and completed lessons are saved in the browser's localStorage under keys starting with "pyplay:", so progress stays on that device.

    Design decision

    No server-side code: the site's README describes the site as zero-backend, hosted statically "to mitigate traditional server-side vulnerabilities", and the playground follows that by running Python in the visitor's browser. Saved progress uses localStorage, wrapped so the page still works if storage is blocked.

    Tradeoffs

    • No accounts or server, so nothing to secure or pay for, but progress lives in one browser and is lost if site data is cleared.
    • Every visitor downloads the Python runtime themselves, so the first visit is slower than a server-run playground would be.
    • In private browsing or with storage blocked, the playground still works but doesn't remember drafts.

    GitHub Pages Hosting

    Static hosting for www.jeremydowdy.com, deployed from the main branch.

    What it does

    Serves every file in the repository as-is. The CNAME file maps the site to www.jeremydowdy.com, and each push to main triggers GitHub's built-in "pages build and deployment" run. There is no build step and no workflow file in the repo; each page is a folder with an index.html.

    Design decision

    Pages are plain folders (/python-playground/, /python-cheat-sheet/, /architecture/) so they work on GitHub Pages without any build tooling. The README gives the reason for static hosting: no server-side attack surface.

    Tradeoffs

    • Deploys are just pushes to main, which is simple, but there's no staging step: whatever is pushed goes live.
    • Generated files (the cheat sheet, the editor bundle, this page's text version) have to be regenerated by hand and committed, because nothing builds them on deploy.

    Cheat sheet page Page

    A static reference page. No Python runtime needed.

    What it does

    Nine sections with 31 example code blocks, a table of contents, and a Copy button on every example. The HTML is generated by python-cheat-sheet/source/generate.py, which can also run every runnable example with real Python before publishing.

    Design decision

    Generated, plain HTML instead of a page built in the browser: the source README says generating it means every example is HTML-escaped the same way and can be tested before it's published. The copy button uses the Clipboard API where it's available and falls back to selecting the text.

    Tradeoffs

    • Content changes mean editing generate.py and re-running it, not editing index.html directly (edits there would be overwritten next time).
    • Examples aren't syntax highlighted, which keeps the page free of JavaScript dependencies but plainer to read.

    Lesson cross-links Links

    URL-hash links that connect each cheat sheet section to its playground lesson and back.

    What it does

    Each cheat sheet section with a matching lesson ends in a "Practice" link to /python-playground/#lesson-id; the playground reads the hash and opens that lesson. In the other direction, each lesson's "Open the Python cheat sheet" link points to the matching section, using the CHEAT_SECTIONS map.

    Design decision

    The two pages are joined by plain links with URL hashes: lessons.js notes that each lesson's id is its URL hash and that the cheat sheet links there. Neither page loads code from the other.

    Tradeoffs

    • Lesson ids are written in three places (lessons.js, CHEAT_SECTIONS and generate.py), so renaming a lesson means updating all three.
    • Strings, built-ins and errors have no lesson yet, so those sections don't get a practice link (Strings links to Lesson 1, which uses f-strings).

    Playground page Page

    The lesson UI: explanation, task, editor, Run / Check / Reset and the output panel.

    What it does

    Shows the current lesson, sends the editor's code to the Python worker when you press Run or Check, streams the output into the panel, highlights errors, and shows pass or fail with a hint. Run and Check stay disabled until the worker reports that Python is ready. If a run takes longer than 10 seconds, it stops the worker and starts a new one.

    Design decision

    The page never runs Python itself; it only talks to the worker with messages. That keeps the page responsive and makes the timeout possible: a stuck worker can simply be terminated.

    Tradeoffs

    • Stopping a runaway program means restarting Python, so the next Run waits a few seconds for it to load again.
    • Each run starts with fresh variables, so code from a previous run can't affect the next one, but you also can't build up state across runs.

    Code editor (CodeMirror 6) Module

    The syntax-highlighted Python editor, bundled into one file.

    What it does

    Provides line numbers, undo history, bracket matching, auto-closing brackets, Python highlighting, 4-space indentation and a dark theme. Ctrl/Cmd + Enter runs the code. It's exposed to the page as PyEditor.create().

    Design decision

    Bundled with esbuild into vendor/codemirror.min.js instead of loaded from a CDN. The vendor README gives the reason: so the playground doesn't depend on a CDN resolving CodeMirror's many small packages.

    Tradeoffs

    • The bundle is a 377 KB file (127 KB gzipped) committed to the repo.
    • Upgrading CodeMirror means rebuilding the bundle by hand with the steps in vendor/README.md.
    • Tab indents code, so keyboard users press Escape, then Tab, to move focus out of the editor (the editor's label says so).

    Lessons data (lessons.js) Data

    The five lessons: explanation, task, starter code and the check for each.

    What it does

    Defines window.LESSONS in order: variables and types, conditionals, loops, lists and dictionaries, functions. Each lesson has an id (its URL hash), title, intro, task, starter code and a check. The expected results live in the check: Python assert statements about the output or variables, whose messages are the hints.

    Design decision

    Expected results are written as Python assertions instead of a fixed expected-output string. That lets a check test variable values and types, ignore extra example output, and re-run the code with other inputs, as the conditionals lesson does with run_with(score=...).

    Tradeoffs

    • More flexible than comparing text, but each check is a small program that has to be written and tested.
    • Lesson content is HTML inside a JavaScript file, so editing it means being careful with quotes and backslashes.

    Python worker (worker.js) Module

    A Web Worker that loads Pyodide and runs the visitor's code.

    What it does

    Loads Pyodide, then runs each program in a fresh namespace. Printed output is batched and sent to the page every 50 ms or 4 KB, and capped at 50,000 characters. Tracebacks are cleaned up so they start at the visitor's own code (main.py), with the source line shown. input() is replaced with a friendly error, since a worker can't read the keyboard.

    Design decision

    The worker file's opening comment gives the reason for the design: running Python in a Web Worker "so a slow or infinite loop never freezes the page", and so the page can terminate it and start a fresh one.

    Tradeoffs

    • input() can't work, because a worker has no way to pause for keyboard input without extra browser features (cross-origin isolation headers) that GitHub Pages doesn't let you set.
    • Output is delivered in small batches rather than instantly, which keeps the page responsive under heavy printing.

    Pyodide runtime (CDN) External service

    CPython compiled to WebAssembly, loaded from the official jsDelivr CDN.

    What it does

    Provides a real Python interpreter in the browser. The worker loads Pyodide 0.29.5 from cdn.jsdelivr.net/pyodide/v0.29.5/full/. Its core files measure 12.3 MB uncompressed (about 5.5 MB gzipped). Only the standard library is used; no extra packages are loaded.

    Design decision

    The version is pinned to one exact release in PYODIDE_VERSION rather than following "latest". Output uses raw (unbuffered) handlers, per the comment in the code, so text printed with end="" isn't lost.

    Tradeoffs

    • The first visit downloads several megabytes before Run is enabled; later visits can come from the browser cache.
    • The playground depends on the CDN being reachable. If it isn't, the page shows an error with a Try again button.
    • Staying on a pinned version means upgrades are a manual change to PYODIDE_VERSION.

    Check logic Module

    Runs the lesson's assertions against the visitor's output and variables.

    What it does

    After the visitor's code runs, run_check executes the lesson's check with the visitor's variables (ns), printed output (output and lines), code, and run_with, which re-runs the code with a variable replaced. A passing check returns passed; the first failed assert returns its message as the hint. If the code itself raised an error, Check fails and asks you to fix the error first.

    Design decision

    Checks run inside the same Python worker as the code they test, so they can inspect real variable values and types, not just printed text.

    Tradeoffs

    • Checks run in the visitor's browser, so a determined visitor could make a check pass without solving it. That's fine for practice, but it isn't a grading system.
    • run_with relies on the starter's top-level assignment line (for example, score = 83) staying in the code; if it's removed, the hint asks the visitor to keep it.
